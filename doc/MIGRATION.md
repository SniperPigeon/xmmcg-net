# 从旧版升级

这是一次性数据迁移，不提供旧竞标 API 或两阶段流程的运行时兼容。原代码保存在 `legacy`；回滚必须恢复迁移前数据库备份并检出旧代码，不能仅回滚代码。生产数据库仍为 SQLite。

## 数据处理

- 谱面从歌曲复制独立标题，保留原资源 key 和投稿者。完整稿、评分中和已评分稿统一为 `submitted`；半成品转为 `archived`。
- 历史两阶段共同作者转为贡献者记录，仍参与“本人不能评分”的排除规则。新投稿只记录提交者，不引入协作创作流程。
- 评分不再依赖竞标轮次；分数转为 Decimal。已有重复的同人同谱评分保留最新一份，原始每条记录留在只读归档。
- 旧竞标、轮次、分配、评分快照、阶段配置和代币余额保存至 `LegacyRecord`；之后移除旧关系、字段和模型。历史谱面另存旧字段快照。
- 老阶段转为仅展示类型，并随原有歌曲、谱面及评分归入已归档的「历史比赛」。原单例比赛配置迁入该届后移除；管理员需要在后台新建并启用新比赛，再配置投稿/评分窗口与可选歌曲阶段。
- 历史 Net 上传状态设为待人工核对，不重新发送已有作品。
- 不自动合并现有用户；大小号关系由今后的验证注册建立。

## 操作

1. 暂停写入，备份实际生产数据库、媒体文件与配置。SQLite 使用数据库的在线备份接口或停机后复制，不单独复制活跃 WAL 数据库文件。
2. 在备份副本上先运行 `manage.py preflight_upgrade`。该命令只读检查已执行迁移与实际表/字段是否相符，发现缺失时停止；不自动造表、fake 迁移或删除数据。
3. 运行 `manage.py migrate`，核对谱面/用户数量、贡献者、资源名称和归档记录。迁移本身不读取或上传媒体。
4. 配置 R2 后导入媒体：

   ```sh
   python manage.py migrate_media_to_r2 --source /path/to/old/media
   python manage.py migrate_media_to_r2 --source /path/to/old/media --apply
   ```

   首条检查所有引用的本地文件是否存在；第二条上传并以 SHA256 校验。保留原对象 key，数据库文件名无需重写。遇到远端同名但不同内容时停止，不覆盖；已匹配的文件跳过。不会删除本地源文件。
5. 配置 CORS、收集静态文件，检查资源读取、谱面包下载、登录和评分导出，再恢复业务。
6. 在后台「比赛」核对「历史比赛」及其成绩导出，再按 [比赛管理与换届](COMPETITIONS.md) 新建、配置并启用新比赛；迁移不会自动开放新一届。
7. 移除旧的阶段更新 cron/systemd 任务。阶段是否进行中现在实时计算，启用开关由管理员控制。

仓库原先提交的 `db.sqlite3` 是陈旧开发样本：它记录 `songs.0001_initial` 已执行，却只有 `songs_song` 表，不能当作符合旧版模型的生产数据库。新版不再跟踪该数据库，也不为它增加专用兼容逻辑。请使用实际生产备份；新安装从空数据库开始。

测试中的迁移演练覆盖符合旧 migration schema 的双作者谱面、重复评分、代币归档和多个谱面的唯一投稿标识。真实部署仍需先运行上述结构预检。

2026-10-26 已使用实际生产 SQLite 的副本完成迁移演练，并逐项比对用户资料、中文公告、署名、评分、评语、真爱票和资源路径。原始 dump 保持不变；迁移和联调均不触发 Net 上传。
